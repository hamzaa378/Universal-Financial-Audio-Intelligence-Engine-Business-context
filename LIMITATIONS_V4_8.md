# v4.8 major limitations, remedies, difficulty, and trade-offs

v4.8 substantially improves the tested precision/recall cases, but it is still a hybrid rules/normalization/context system operating on ASR output. The table below separates detector limitations from deployment and evaluation limitations.

Difficulty scale:

- **Low** — isolated code/config change, usually hours to about a day.
- **Medium** — multiple modules plus regression expansion, usually days.
- **High** — new model/data subsystem, language/profile architecture, or significant evaluation effort.
- **Very High** — production-grade research/data engineering problem with broad validation requirements.

| # | Major limitation in v4.8 | Possible way to rectify it | Difficulty | Likely negative effects / trade-offs |
|---|---|---|---|---|
| 1 | **ASR errors can cause complete privacy misses.** If Whisper never transcribes a phone number, name, account, or secret correctly, the text PII layer cannot reliably recover it. | Use a privacy-oriented ASR lattice or N-best decoding for candidate regions; preserve alternate digit/alphanumeric hypotheses; add confidence-triggered re-decode on short suspected PII windows. | High | More GPU work, higher latency, more memory, and alternate hypotheses can increase false positives if accepted too aggressively. |
| 2 | **English/Hinglish-oriented context grammar.** Clause ownership, example suppression, public-geography language, and expected-type responses are mostly English-centric. | Add language-specific policy modules selected from language ID; train/evaluate multilingual intent/role classifiers; maintain locale-specific phrase banks. | High | Larger maintenance burden, more model size, extra inference cost, and cross-language ambiguity can reduce precision. |
| 3 | **Indian financial/identity coverage is much stronger than global coverage.** PAN, Aadhaar, IFSC, UPI and Indian DL logic are specific; other countries' tax IDs, bank routing formats, national IDs and licence formats are incomplete. | Introduce modular country/region profiles with validators, checksums, ownership terms and benchmark suites per jurisdiction. | High | Rule count and policy complexity grow quickly; wrong locale selection can cause both misses and false positives. |
| 4 | **PUBLIC_GEO_CONTEXT is lexical, not geographic reasoning.** It handles tested phrases such as `postal code 411001 covers part of Pune`, but unusual public-postcode phrasing may still mask, and unusual personal phrasing may be vetoed incorrectly. | Add a lightweight local semantic role classifier for `PERSONAL_ADDRESS` vs `PUBLIC_LOCATION`, optionally aided by offline city/postcode gazetteers. | Medium–High | Gazetteers add data size/updates; semantic models add latency; overconfident public-location classification could create privacy false negatives. |
| 5 | **Address parsing is heuristic and bounded.** Very long, multi-line, international, non-Latin, PO-box-only, landmark-heavy, or punctuation-poor addresses can still be missed or over-captured. | Replace/augment the address span builder with a trained address/NER parser plus structural post-processing; add country-specific address grammars. | High | NER may mask ordinary location mentions; larger spans can over-redact; multilingual models add latency and memory. |
| 6 | **Partial identifier protection is deliberately narrow.** v4.8 handles explicit owned last-four card/account forms, but not every phrasing (`****1111`, `ending one one one one`, last two/six digits, `card suffix 1111`, etc.). | Add a configurable partial-identifier grammar and spoken partial-digit normalizer, still requiring strong ownership evidence. | Medium | Expanding four-digit grammars is one of the easiest ways to reintroduce numeric false positives (amounts, years, OTPs, reference numbers). |
| 7 | **One-sentence expected-type state is intentionally short-lived.** It misses valid replies after an intervening sentence or a long conversational detour. | Replace the one-sentence TTL with a small typed discourse state machine keyed by speaker/turn, with explicit consume/reset rules and confidence decay. | Medium–High | Longer state can attach a field request to the wrong later number, increasing false positives and potentially masking unrelated business data. |
| 8 | **ASR punctuation affects sentence/clause boundaries.** Missing punctuation, comma errors, or incorrect sentence breaks can weaken the expected-type state or merge unrelated clauses. | Use pause/timestamp segmentation in addition to punctuation; infer field boundaries from labels and token timing; optionally use a lightweight punctuation-restoration model. | Medium | More preprocessing and models add latency; incorrect restored punctuation can create new context errors. |
| 9 | **NAME masking still depends on ownership/context.** This intentionally avoids hiding every public person's name, but unlabeled personal names, single-token names, uncommon names, or indirect self-identification can be missed. | Use token NER as candidate generation plus a speaker/ownership classifier; integrate diarization to distinguish the caller's identity from agent/public names. | Medium–High | NER tends to detect many harmless names; stronger name masking can noticeably increase false positives and over-redaction. |
| 10 | **Secret/API-key detection cannot know every proprietary format.** Unknown short secrets, custom tokens, or low-entropy credentials can be missed. | Add user/company configurable secret schemas; prefix libraries; entropy/context scoring; optional local secret-scanner plugin. | Medium | Broader secret scanning can mask hashes, UUIDs, filenames, build IDs, or random test data; organization-specific configuration requires maintenance. |
| 11 | **Operational IDs are off by default.** Ticket, order, complaint, customer and transaction IDs can be sensitive in some organizations even though v4.8 avoids treating them as core PII by default. | Provide policy profiles such as `Personal PII`, `Financial + PII`, `Enterprise confidential`, with per-ID toggles. | Low | Enabling them increases over-masking of normal operational conversations and makes demos look more aggressive. |
| 12 | **Checksum/format validation is not proof of real-world identity.** Some context-gated values can be masked even if a checksum is unavailable or intentionally invalid in synthetic/test data. | Use per-type validation tiers: strict checksum, format-only, and context-only; expose policy threshold by environment. | Low–Medium | Strict validation can leak mistyped but still-sensitive real values; loose validation increases false positives. |
| 13 | **Audio redaction depends on ASR token timing/alignment.** Character-to-token mismatch, word-timestamp errors, overlap, or rapid speech can leave a small audio edge exposed or mask extra neighboring speech. | Use forced alignment/CTC alignment for accepted PII spans; adaptive padding based on alignment confidence; speaker-aware interval ownership. | High | More computation and latency; larger padding hides more non-sensitive audio; forced alignment may require another model. |
| 14 | **Overlapping speakers/crosstalk remain difficult.** One speaker can say PII while another speaks simultaneously, and mono ASR timing may not isolate the sensitive source cleanly. | Enable/upgrade diarization and speaker-attributed ASR; for stereo calls, preserve channel separation and redact per channel. | High | Diarization is expensive, can be inaccurate on short turns, and adds model/runtime complexity. |
| 15 | **The detector protects transcript/audio content, not arbitrary on-screen visual PII.** A phone number visible in a screen share but never spoken is outside this program's current audio/text pipeline. | Integrate a separate screen privacy pipeline using UI accessibility data + OCR + layout ownership + visual masking. | Very High | Large scope increase; OCR/layout latency; GPU contention with ASR; synchronization between visual and audio protection becomes complex. |
| 16 | **Synthetic benchmark success does not establish real-world accuracy.** Current regression suites are deliberately constructed and relatively small. | Build consented/synthetic-but-realistic labeled audio across accents, noise, devices, languages, disfluencies, call domains and adversarial negatives; report per-type precision/recall and leakage duration. | High–Very High | Data collection/labeling cost, privacy governance, annotation disagreements, and slower development cycles. |
| 17 | **Optional semantic/NER AI can change latency and behavior.** The deterministic tests do not measure every optional model combination. | Maintain separate CI benchmark profiles for rules-only, semantic-on, NER-on, and both-on; calibrate thresholds per profile. | Medium | More CI time and hardware variability; model updates can cause regression drift. |
| 18 | **Raw PII exists briefly in process memory before masking.** The tool protects outputs, not a compromised host/process. | Minimize retention, disable raw logging by default, zero sensitive buffers where practical, encrypt stored artifacts, isolate the process, and apply OS access controls. | Medium | More engineering complexity; zeroization is imperfect in managed/Python memory; stricter isolation complicates debugging. |
| 19 | **Policy ambiguity cannot be solved purely technically.** A postal code, employee ID, transaction ID, or last-four digits may be sensitive in one organization and non-sensitive in another. | Add policy profiles and per-entity controls, with organization-specific configuration and audit tests. | Low–Medium | More settings can confuse users; overly permissive profiles leak data while overly strict profiles over-mask. |
| 20 | **Performance claims for the text detector do not equal end-to-end realtime performance.** ASR/GPU decode, optional AI, audio loading, diarization and output encoding dominate latency. | Benchmark real streaming chunks and report p50/p95 end-to-end latency, RTF, GPU memory and masking delay separately from text-classifier time. | Medium | Benchmarking becomes hardware-specific; chunking for lower latency can reduce ASR context and therefore accuracy. |

## Highest-value next improvements

If the goal remains **higher recall without sacrificing v4.8 precision**, the next upgrades should be prioritized as follows:

1. **P0 — real-audio benchmark + leakage-duration metric.** The largest unknown is now ASR/alignment behavior rather than the synthetic text classifier.
2. **P0 — timestamp/pause-aware sentence and clause segmentation.** This directly hardens the v4.7/v4.8 context architecture against imperfect ASR punctuation.
3. **P1 — configurable policy profiles.** Separate core PII, financial secrets, partial identifiers, and operational IDs rather than forcing one sensitivity definition.
4. **P1 — multilingual/locale modules.** Add language and country profiles incrementally, each with its own regression suite.
5. **P1 — forced alignment for audio redaction.** Use only for accepted PII spans so audio privacy improves without adding a large cost to every word.

## Changes that should be approached cautiously

The following ideas may improve recall but can easily damage the false-positive rate if applied globally:

- masking every 4–6 digit number;
- masking every valid PAN/IFSC/card-like shape without ownership;
- retaining expected-type state for many sentences;
- masking every PERSON entity returned by NER;
- treating every public postal code as personal;
- increasing semantic-model weight above explicit deterministic ownership/validator evidence.

v4.8 deliberately avoids those global-aggressiveness changes.
